# FlexAgent vs LangChain4j vs Spring AI

为了帮助开发者理解 FlexAgent 与市面上主流 Java 大模型框架的区别，本篇将从架构、原理解耦、推理流支持以及混合调试等维度进行深入比对。

---

## 1. 核心架构对比

| 维度 | FlexAgent | LangChain4j | Spring AI |
| :--- | :--- | :--- | :--- |
| **设计定位** | **轻量级 Agent 运行时适配器**，专注于工具解耦与本地/远程混合调试 | 强耦合、大而全的 **LLM 应用集成框架**，地位类似于 Java 界的 LangChain | 强耦合、全家桶式的 **Spring 生态 AI 集成包**，采用 Spring 声明式规范 |
| **解耦程度** | **极高**（业务 `@Tool` 不依赖具体底座大模型框架） | **一般**（绑定各自底座框架的 API 与反射注解） | **一般**（深度绑定 Spring Container 依赖注入） |
| **推理流优化** | **原生支持**（内置流式 `<think>` 提取状态机） | **需手写**（流式传输下无原生回溯过滤，需开发者自提） | **需手写**（同上） |
| **混合调试** | **支持**（支持一键切换 Go 编写的 localharness 引擎） | **不支持**（完全运行在 JVM 进程内） | **不支持**（同上） |
| **生态丰富度** | **较低**（本身需要通过桥接模式集成底层底座框架） | **极高**（拥有完备的向量库、RAG、组件生态） | **极高**（Spring 官方背书，天然融合微服务组件） |

---

## 2. 深入原理解析

### 2.1 工具解耦模式
* **LangChain4j / Spring AI**：
  在传统的开发中，你必须将业务工具方法用底座的 `@Tool` 注解修饰，并由该底座的反射核心负责解析与调度。当你的项目需要从 LangChain4j 迁移到 Spring AI 时，你会发现整个业务逻辑层都需要因为 `@Tool` 和 `ChatClient` 的参数不同而全部重写。
* **FlexAgent**：
  它抽离了统一的 `ToolDefinition`，通过 `ToolAdapter` 自主负责反射的执行与入参映射。业务方法只需用最基础的方法注解修饰（目前优先做 langchain4j 原生兼容，未来会推出无任何三方包依赖的 `@FlexTool`），从而在更换底座模型运行时，业务类无需任何逻辑改写。

### 2.2 推理思维流分段支持 (xml-think-tag-extractor)
* 当我们调用带有思考过程的大模型（如 DeepSeek-R1、Qwen-based 推理版等）时，流式响应会以碎片包（chunks）的形式吐出类似 `<think>思考过程</think>最终回答` 的结构。
* 传统的 SDK 只能将这段文本一股脑投递给用户，导致用户界面将思考过程与回复正文合并，且容易在网络丢包、延迟等状况下导致 `<think>` 标签被截断。
* **FlexAgent** 独家实现了 `XmlThinkTagExtractor` 状态机。它在流式字符拼装过程中，能即时在内存中处理标签边界，即使发生字符切碎（如 `<thi` 与 `nk>` 被分在两个 chunk 吐出），仍能保证将思考输出独立发布为 `ThinkingDelta`，而将普通文本发布为 `TextDelta`。

### 2.3 容错策略 (ToolCallPolicy)
* 大模型在长上下文或者受到微小干扰时，输出的 Function Call 容易产生 JSON 幻觉。
* **FlexAgent** 提供了多级降级：
  * `STRICT`：一旦格式解析错误，立刻向大模型发送解析失败错误。
  * `LENIENT`：自动去除首尾可能多余的 Markdown 代码块标签（如 ```json ... ```），容忍空字段。
  * `TEXT_FALLBACK`：大模型由于幻觉把 JSON 写成了白话，或者未按照 Function Call 协议输出，而是输出了普通文本时，适配层自动将这段文本回退并模拟为 ToolResult 的反馈，保障 Agent Loop 不会因为反序列化异常崩溃。
